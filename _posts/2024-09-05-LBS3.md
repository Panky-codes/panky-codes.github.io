This is a multipart series where I will be going over the support of
Large block sizes(LBS) in Linux. Checkout the previous articles from 
[LBS series](https://blog.pankajraghav.com/tag/lbs) before proceeding with this article.

In this blog post, we will cover the implementation of the latest round of 
LBS patches that have been sent to the Linux kernel which are in the process of getting
mainlined soon.

Just to reiterate the issue with LBS support in Linux:
- Historically, page cache was closely tied to a PAGE.
- No support to track the “blocks” > page size as a single unit in the
  page cache to avoid eviction of partial blocks.

### Large folio support in the page cache:

Linux kernel has had the support to the compound page allocation for a
long time, but a struct page became an overloaded term as it could mean
a head page or a tail page, etc.

Folios were added to the Linux kernel 5.16 as structure that can
represent one or more pages, but it represents either order-0 page or
the head page of a compound page (large folio).

Page cache got the support for large folios in Linux [5.18](https://lore.kernel.org/lkml/20220116121822.1727633-1-willy@infradead.org/).
This support creates large folios in the readahead and fault paths when
large folios mapping is enabled by the filesystem. The first filesystem
to enable this was XFS. Note that this is an **optimization** based on
the size of the readahead and the memory pressure.

This support is really crucial for LBS as page cache is not anymore tied
to "PAGE" anymore.

Matthew Wilcox on why large folios is important for LBS support in Linux:
```
The important reason to need large folios to support large drive
block sizes is that the block size is the minimum I/O size. That
means that if we're going to write from the page cache, we need the
entire block to be present. We can't evict one page and then try to
write back the other pages -- we'd have to read the page we evicted
back in. So we want to track dirtiness and presence on a per-folio
basis; and we must restrict folio size to be no smaller than block
size.
```
### Missing piece in the puzzle for LBS XFS:
IOMAP aleady supports large folios and it got further optimizations to
create large folios in the [buffered IO write path](https://lore.kernel.org/linux-fsdevel/20230710130253.3484695-1-willy@infradead.org/).

The only missing piece to add LBS support to XFS was the ability of the
filesystem to request minimum order of allocation in the page cache.
With the minimum order support in the page cache, filesystem can
allocate blocks that are greater than the page size to be tracked as
"one" unit.
