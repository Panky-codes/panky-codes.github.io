Writes to a storage device is considered **atomic** when the IO
travels from userspace to the device in an "untorn" state under any
conditions. Untorn here refers to no partial IO transfer, either the
whole IO is present in the device or none at all.

Atomic IO is important for critical applications such as
databases to make them more reliable. Without this atomic IO guarantee, 
databases will resort to extra logging to make the application more 
reliable. We will focus the discussion on atomics around databases, as
they require the atomicity guarantee to be reliable.

## Understanding torn I/O issue in databases:
```
      [ Database Application (MySQL/PG) ]
                  |  
                  |  1. 16KB/8KB Page Dirty in Buffer Pool
                  V
      [ Linux VFS / Filesystem Layer ]
                  |
                  |  2. Page fragmented into 4KB segments (FS Blocks)
                  V
      [ Linux Block Layer / Scheduler ]
                  |
                  |  3. Segments merged/split into BIOs
                  V
      [ NVMe/SCSI Driver & Controller ]
                  |
                  |  4. Data lands in SSD DRAM Cache (Volatile!)
                  V
      =================================== <--- Power Loss Zone
      [ Physical NAND Flash Media ]
```
Relational databases like MySQL and PostgreSQL work on database pages
(DB pages). Each DB page stores a bunch of data along with extra metadata
about the data. All the DB pages are also checksummed to detect
corruption. It is important to understand that databases depends on
the fact that all DB pages are always intact. If a DB page is corrupted, then the
database has to do recovery to replace the corrupted block. Each database have different default DB page sizes. MySQL has
16KB as the default DB page size while PostgreSQL has chosen 8KB as the
default DB page size. 

As indicated in the image above, there are different layers that are
involved when the IO travels from the database to the actual non-volatile
storage. As a lot of things can go wrong that can result in a single
database page being torn before it reaches the storage device, databases
employ different torn write protection mechanism.

PostgreSQL uses a technique called [Log Page on First
Write](https://transactional.blog/blog/2025-torn-writes#_log_page_on_first_write). MySQL uses a
technique called [Double-Write Buffering](https://transactional.blog/blog/2025-torn-writes#_double_write_buffer).
In essense, these technique involves writing the same data twice which
can reduce the lifetime of a device and reduce the bandwidth.

If the storage device and the operating system can expose atomic IO APIs that can
be used by databases, then they can avoid the extra writes needed
for torn write protection by offloading the responsibility. This is
great news for consumers of databases as this can reduce the number of
writes that go to a device, thereby, increasing the lifetime and
decreasing extra IO overhead.

## Atomic I/O in NVMe:
Achieving end-to-end atomic support requires operating system and device
support. Operating system support will be discussed in detail in the
next article. This section will be used to elaborate atomics support in NVMe devices.

Unlike SCSI, which uses a distinct command (WRITE ATOMIC), NVMe support
is implicit. If a write request adheres to specific size and alignment
rules defined by the controller, the drive guarantees atomicity,

NVMe exposes two critical parameters:
- AWUN (Atomic Write Unit Normal): The max size guaranteed to be atomic
during normal operation.
- AWUPF (Atomic Write Unit Power Fail): The max size guaranteed to remain
atomic even during a power loss. This is the critical value for databases.

### AWUN:
NVMe controller can decide to execute commands in parallel that might
have overlapping LBA ranges. AWUN's primary purpose is to control the 
atomicity of command execution in relation to other concurrent commands. By enforcing inter-command serialization,
AWUN prevents a situation where multiple parallel writes from different threads
interleave, which could result in logical blocks containing a partial mix of
data from one command and partial data from another.

It is important to note that AWUN specifically governs normal, active operations;
it does not guarantee protection against torn writes caused by a power failure
or error condition (that scenario is governed by a different parameter, AWUPF).

The [AWUN support](https://patchwork.kernel.org/project/qemu-devel/cover/20240926212458.32449-1-alan.adamson@oracle.com/)
in QEMU serializes the commands if the LBA ranges are overlapping
(reading qemu nvme emulation code is a great way to understand how the
nvme controller works under the hood).

### AWUPF:
AWUPF is a parameter defined in the NVMe specification that indicates 
the maximum size of a write operation that the storage controller 
guarantees will be written atomically to the non-volatile media, 
even if a power failure or error condition interrupts the write.

While AWUN (Atomic Write Unit Normal) governs the interleaving of 
parallel commands during normal operations, AWUPF specifically dictates 
the behavior of the drive during catastrophic interruptions. Because 
operating systems and databases rely on this feature for data integrity 
and crash recovery, the Linux kernel prioritizes the AWUPF value when 
reporting atomic limits to applications

Many enterprise SSDs are built with capacitors that store enough residual
electrical charge to keep the drive powered for a brief moment after
main power is lost. This allows the drive's controller to finish writing
any in-flight data or flush its volatile DRAM cache to the non-volatile
NAND flash media before shutting down completely

Visualizing the Guarantee If a Database Page Size ≤ AWUPF, the hardware
ensures the following outcome during a crash,:

```
Scenario: Overwriting "Old Data" with "New Data" (16KB) during Power Loss

       [ Physical Media Sectors ]
       | 0 | 1 | 2 | 3 |
       -----------------

WITHOUT ATOMICITY (Torn Write):
Result: | New | New | Old | Old |  <-- CORRUPTION (Mixed State)

WITH NVMe AWUPF (Atomic Write):
Result: | New | New | New | New |  <-- SUCCESS (Fully Written)
             OR
Result: | Old | Old | Old | Old |  <-- ROLLBACK (Nothing Written)

```
The application will never see a partial mix; it is strictly all-or-nothing
